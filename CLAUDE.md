# GlowTrack

Progressive Web App — лична енциклопедия за козметични процедури + дневник +
напомняния. Живо на **https://glowtrack.eu** (GitHub Pages + custom domain
през `CNAME` файла).

Собственик/потребител: физическо лице. Комуникацията за развитие на
приложението е **на български**. Интерфейсът е двуезичен (бг/en).

Позициониране: "Know your glow." — справочник за 383 процедури (какво е, преди/
след, противопоказания, интервали) + личен дневник със снимки, цени и оценки +
push напомняния за следваща сесия. Има и B2B страна (клиники/брандове/
дистрибутори/обучителни центрове), която засега е само landing + запитване.

## Технически стек

- **Единствен файл `index.html`** — ~11 000 реда / **~1.92 MB**: HTML +
  `<style>` + 10 инлайн `<script>` блока. Няма модули, няма компоненти,
  няма framework.
- **ИМА build стъпка** (за разлика от iForget!) — `npm run build` →
  `scripts/build.mjs` → `dist/`. Виж отделния раздел по-долу, това е първото,
  което трябва да се знае преди каквато и да е промяна.
- **Firebase** — Auth (имейл+парола), Firestore, Storage, Cloud Messaging
  (push), Analytics, Cloud Functions.
- **Sentry** (browser bundle 10.63.0 от CDN, `tracesSampleRate: 0`) — само
  грешки, без performance трейсове.
- **Service worker `sw.js`** — кеширане на обвивката + Firebase Messaging в
  ЕДИН файл (виж защо по-долу — това е било източник на дълга поредица бъгове).
- **localStorage** — целият личен state се пази локално и се огледава във
  Firestore (не обратното). Приложението работи офлайн за четене.
- Шрифтове: Cormorant Garamond (заглавия, serif) + DM Sans (текст) от Google
  Fonts, през `@import` в началото на `<style>`.

### ВАЖНО: Firebase проектът НЕ се казва "glowtrack"

Project ID е **`after-care-treatment`** (историческо име отпреди ребрандирането).
Среща се навсякъде — `.firebaserc`, `firebase.json` конфигурацията, storage
bucket-а, authDomain-а, имената на GitHub Actions secrets-ите, дори в
`.env.after-care-treatment` файла, който CI генерира. **Не се "поправя"** —
смяната на project ID означава нов Firebase проект и загуба на всички данни.
Ако някъде видиш `after-care-treatment` — това е GlowTrack, не друг проект.

## Деплой и build

### `npm run build` (`scripts/build.mjs`)

Източникът на истината е `index.html` в корена; build-ът пише в `dist/`
(git-игнориран). Какво прави:

1. Минифицира всеки инлайн `<script>` блок поотделно с **terser**.
2. Минифицира целия HTML с **html-minifier-terser** (`minifyCSS: true`,
   `minifyJS: false` — JS-ът вече е минифициран).
3. **Проверява, че всички имена на функции, викани от инлайн `onclick=`/
   `onchange=`/... атрибути, са оцелели** (`verifyHandlerNamesSurvive`) —
   в момента **166 такива имена**. Ако някое липсва в изхода, build-ът
   ГЪРМИ, вместо да произведе тихо счупена страница.
4. Копира само `PASSTHROUGH_FILES` (CNAME, иконките, og-image, manifest.json,
   sw.js) и `PASSTHROUGH_DIRS` (`images/`, рекурсивно). Всичко останало
   (`functions/`, `*.py`, `firebase.json`, `firestore.rules`, `CLAUDE.md`) НЕ
   отива публично. И двата списъка са ИЗРИЧНИ — нов файл/папка в корена няма
   да излезе на живо, докато не се добави тук.

Резултат: ~1922 KB → ~1784 KB (**само ~7% по-малко**). Не е разочароващо —
почти целият файл е ДАННИ (текстовете на 383 процедури + две base64
снимки), а данни не се минифицират.

**Защо `toplevel: false` в terser опциите е задължително:** приложението
закача интерактивността си през голи имена в `onclick="..."` атрибути на
статичния HTML. Terser вижда само съдържанието на `<script>` блоковете, не
атрибутите — с `toplevel: true` би преименувал/изхвърлил именно тези функции
и всеки бутон в приложението би спрял да работи. Пазачът от стъпка 3
съществува точно за да улови такава регресия.

**`terserOptions()` е ФУНКЦИЯ, не споделен обект** — terser мутира вложените
`compress`/`mangle` обекти на място, така че преизползване на един и същ
референс между извикванията (по едно на `<script>` блок) тихо поврежда
следващите.

### GitHub Actions

- **`.github/workflows/static.yml`** — при push към `main` (или ръчно):
  Node 22 → `npm ci` → `npm run build` → deploy на `dist/` към GitHub Pages.
  `concurrency: cancel-in-progress: true` — бърза серия push-ове не чака
  старите deploy-и.
- **`.github/workflows/deploy-functions.yml`** — при push към `main`, но САМО
  ако са пипнати `functions/**`, `firebase.json` или `.firebaserc`.
  Деплойва с `npx firebase-tools@13.29.1 --token`.

  **Капанът с `.env` файла в CI (два пъти чупен, поправен):** `firebase
  deploy` в non-interactive режим не може да прочете `defineString` params
  (`SMTP_HOST`/`SMTP_PORT`) без локален `.env.<project-id>` файл — затова
  workflow-ът го генерира от GitHub secrets. Но `defineSecret` params
  (`ANTHROPIC_API_KEY`/`SMTP_USER`/`SMTP_PASS`) **НЕ бива да са в същия
  файл** — Cloud Run гърми с "Secret environment variable overlaps non
  secret environment variable". Стойността им живее само в Secret Manager
  (`firebase functions:secrets:set`).

## Модел на данните

### Firestore колекции

| Колекция | Кой пише | Бележки |
|---|---|---|
| `users/{uid}` | собственик + Admin SDK | профил + целият личен state |
| `diary_entries/{id}` | собственик | по един документ на запис (НЕ масив в users) |
| `feedback/{id}` | всеки логнат (create), админ (чете) | валидация в rules: `text` 1–2000 знака, `type` ∈ idea/bug/content |
| `app_config/settings` | само админ | `aiAssistantEnabled` feature flag; публично четим |
| `clinic_ads/{id}` | само админ | реклами на клиники, публично четими |
| `product_ads/{id}` | само админ | афилиейт продукти, публично четими |
| `affiliate_clicks/{id}` | всеки логнат (create) | статистика за кликове |
| `search_logs/{id}` | всеки логнат (create) | топ търсения за админ таблото |
| `clinic_inquiries/{id}` | **всеки, дори нелогнат** (create) | B2B запитвания от `#for-clinics` |
| `referrals/{id}` | логнат (create, само `status:'pending'`) | update/delete забранени на клиента |
| `meta/**` | само Admin SDK | брояч на потребители, идемпотентност на тригери |
| `password_reset_throttle/**` | само Admin SDK | rate limiting |

`meta` и `password_reset_throttle` НЯМАТ собствен блок в `firestore.rules` —
падат в catch-all `match /{document=**} { allow read, write: if false; }`,
което е правилното (Admin SDK заобикаля rules изцяло).

### `users/{uid}` — полета

Клиентски (собственикът пише):
`uid`, `name`, `email`, `createdAt`, `lang`, `dob` (YYYY-MM-DD), `gender`,
`onboarded`, `favs[]`, `diaryOrder[]`, `skinType`, `fototype`, `skinTestDate`,
`cycleData`, `notifs[]`, `calEvents[]`, `nextReminderAt`, `fcmToken`,
`fcmTokenUpdatedAt`, `referralCode`, `referredBy`, `aiUsage` (пише се
сървърно, но живее тук).

**Server-only полета — клиентът НЕ може да ги пипа (заключени в rules):**
`referralCount`, `unlockedRewards`, `sentNotifIds`. Плюс `lastBirthdayYear`
(пише се само от `sendBirthdayNotifications`).

### `diary_entries/{id}`

```
{ userId, procId, procName, procIcon, clinic, specialist, contact,
  advice, feeling, products, price, rating,
  photos[], photosBefore[], photosAfter[],   // Storage URL-и
  createdAt, isRoutine? }
```
`procId: 'skin-routine'` + `isRoutine:true` е псевдо-запис от домашната грижа
(автоматичен при пълна дневна рутина), не истинска процедура.

### Напомняне (`notifs[]` / localStorage `gt_notifs`)

```
{ id, procId, procName, date:'YYYY-MM-DD', time:'HH:MM',
  type:'reminder'|'booking'|'calendar', isTest? }
```
`type:'calendar'` е push "сянка" на календарно събитие — id-то е предвидимо
`'n_cal_'+ev.id`, за да може да се намери/обнови/изтрие еднозначно.

### Календарно събитие (`calEvents[]` / `gt_cal_events`)

```
{ id:'cev_'+ts, date:'YYYY-MM-DD', title, time, note, color, isTest? }
```

### `cycleData`

```
{ periods:[{start,end}], symptoms:{ 'YYYY-MM-DD': [tag,...] }, cycleLength:28 }
```
Стар формат (`periods` като масив от голи низове) се мигрира автоматично при
четене в `_loadCycleData()` — не го чупи.

### localStorage — ТРИ различни конвенции за ключове (внимавай)

1. **През `_lsKey()`** → `<base>_<uid>` или `<base>_guest`. Ползва се от
   `_lsGet`/`_lsSet`/`_lsRem`: `gt_notifs`, `gt_cal_events`, `gt_favs`,
   `gt_diary_order`, `gt_cycle`, `gt_skin_test`, `gt_archetype_test`,
   `gt_offcache_*`.
2. **Ръчно вграден uid** — `'gt_care_'+(uid?uid+'_':'')+type+'_'+today`,
   `'gt_routine_'+...`. Прави същото, но по друг начин.
3. **Изобщо без uid** (споделя се между акаунти на едно устройство):
   `gt_fav_cats`, `gt_custom_routine`, `gt_care_custom_<type>`,
   `gt_routine_last_date`, `gt_routine_custom_<date>`, `gt_step_product_*`,
   `gt_notif_date`, `gt_active_cat`, `gt_dark`, `gt_lang`, `gt_rosegold`,
   `gt_intro_seen`, `gt_last_page`, `gt_pending_ref`, `gt_test_mode`,
   `gt_clinics_lang`, `gt_profile_first_flip_done`.

Група 3 е смесена: за `gt_dark`/`gt_lang`/`gt_active_cat` това е нарочно и
правилно (настройка на УСТРОЙСТВОТО, не на акаунта). За персонализираните
стъпки в домашната грижа (`gt_custom_routine`, `gt_care_custom_*`) и за
любимите категории (`gt_fav_cats`) обаче е несъответствие — на споделено
устройство втори акаунт вижда чуждите стъпки. **При нова функция ползвай
конвенция 1** (`_lsGet`/`_lsSet`), освен ако наистина не искаш нещо
устройство-специфично.

### `alsoCat` — процедура в ПОВЕЧЕ от една категория

`cat` е основната категория (тя се показва в заглавието на sheet-а и отива в
analytics). `alsoCat:['hair']` добавя записа и към чуждия филтър, БЕЗ да го
мести. Реализирано на две места: `catOk` в `renderProcs()` и `catLbl` в
`procSearchHaystack()` (за да се намира и по името на втората категория).

Ползва се за **лазерната епилация**, която беше разкъсана: александритов,
диоден и Nd:YAG лазер (по лице/тяло) живееха в "Коса и нокти", а общата
лазерна, електро-, SHR, E-light, диодна, Altesse и Epilfree — в "Апаратни".
Двете групи следваха различна логика (апарат × зона срещу само апарат) и се
припокриваха буквално: "Диоден лазер" и "Диодна епилация" са един и същ
810nm апарат; Altesse Е александритова система. Потребител, отворил "Коса и
нокти", не виждаше SHR и електроепилацията; отворил "Апаратни" — не виждаше
Nd:YAG варианта.

Маркирани са 16 записа (8 в едната посока, 8 в другата). Ако добавяш нова
процедура за епилация, реши в коя категория е ОСНОВНА и добави другата в
`alsoCat`.

категория); нула JS грешки.

### Търсенето включва `devices` — не го махай

`procSearchHaystack()` търси в name/sub/subcat/what/zones/results/contra/tags,
EN полетата И **`devices`**. Последното беше добавено, след като се оказа, че
**301 от 557 имена на апарати не се намират изобщо** — Candela, Cynosure,
Alma, Lumenis, InMode, NormaTec и т.н. живеят САМО в `devices`. Каталогът е
справочник: човек, на когото в салона са предложили "Vacuslim", трябва да го
намери. Без това дедупликацията по-долу би направила слетите марки невидими.

### Фонетично търсене кирилица⇄латиница — `toLatin()`/`CYR_TO_LAT`

По изрична заявка: търсенето трябва да намира "Fotona", докато потребителят
пише "фотона" на кирилица (и обратно). Реален разрив в данните — имената на
процедурите са на кирилица, но марките на апаратите в `devices` (виж по-горе)
живеят изцяло на латиница; буквално `includes()` съвпадение никога не
свързва двете писмености.

Решението е СЪЩАТА транслитерационна схема, вече доказана в iForget
(`toLatin()`/`textMatches()` там) — официалната БГ кирилица→латиница
таблица (`CYR_TO_LAT`), пренесена 1:1. В `renderProcs()`, за всяка дума от
заявката: първо директно `hay.includes(w)`, после разпознат синоним
(`SEARCH_SYNONYMS`), и чак ако и двете пропаднат — `toLatin(hay).includes(
toLatin(w))`. `hayLatin` се смята МЪРЗЕЛИВО (`let hayLatin=null`, само при
първия неуспешен опит за дадена процедура), за да не се транслитерира целият

### ПРАВИЛО: снимка НИКОГА не влиза сурова

Всяка нова процедурна снимка се преобразува ПРЕДИ да влезе в repo-то:
**800px по широчината, JPEG, quality 82 (mozjpeg)** — това дава ~50 KB и
съвпада с конвенцията на заварените в Storage (800x533, ~32 KB).
Изходните файлове са 1200px PNG по ~1.3 MB, тоест разликата е ~25x; 56

Преобразуването става със `sharp` (не се държи в `package.json` на проекта —
инсталира се временно, това не е build зависимост):
```
sharp(src).resize({width:800, withoutEnlargement:true})

```
Внимавай: част от подадените файлове са JPEG с разширение `.png` — `sharp`
се оправя сам, но изходът винаги се именува `.jpg`.

същата причина като при регистрацията на `sw.js`: работи и ако приложението
някога живее в поддиректория.

### ПРАВИЛО: смяна на вече качена снимка = НОВО име, не презапис

`sw.js` е cache-first за same-origin статика и чисти кеша само при смяна на
`CACHE` версията. Презапишеш ли файл на СЪЩИЯ адрес, всеки, който вече го е
отворил веднъж, остава със старата снимка на практика завинаги — новата няма
да се дръпне, защото адресът не се е променил.
Затова втора версия получава суфикс: `..._kriolipoliza.jpg` →
`..._kriolipoliza_v2.jpg`, старият файл се трие от repo-то. Смяната на адреса
е това, което гарантира, че всички виждат новата.

### `forlle-hydra` — реален бъг с частично незареждаща се външна снимка

Потребителят докладва на реален iPhone (Safari, live сайт): голямото
16:9 hero изображение в горната част на sheet-а показваше лявата
половина като истинска снимка, а дясната — като плътен незапълнен
тъмносив блок. Първоначалната ми диагноза (по-рано в разработката) беше
грешна — гледах само малката 44px икона (`sh-icon`, `object-fit:cover`)
и предположих зле композиран маркетингов колаж (продукт + плътен цвят),
изрязан лошо на малък размер.

Истинският елемент е ДРУГ — самото 16:9 hero изображение, СЪЩО
`object-fit:cover`. Тъкмо това обръща диагнозата: `cover` по
дефиниция НЕ МОЖЕ да остави празно/незапълнено място — то винаги
разпъва снимката да покрие цялата рамка. Значи "половин цвят" не може
да е резултат от лошо изрязване. По-вероятната причина: външният адрес
(`cdn.enter.pro/.../glowtrack_forlled_hydration_00b24ce3.png`) не се е
заредил докрай на устройството на потребителя — прекъснато/бавно
теглене на external CDN снимка, извън наш контрол.

Решението е същото като при всички други внесени процедурни снимки,
независимо коя от двете диагнози е вярната: снимката стана СОБСТВЕНА,
локална (`images/face/forlle-hydra.jpg`, 800px, JPEG q82, mozjpeg,
доставена лично от потребителя), вместо да разчита на нечий чужд
сървър. `forlle-hydra` няма `PROCS_EN` запис изобщо, значи няма нужда
от чистене на EN `img` поле. Проверено с Playwright върху build-натия
`dist/`: `naturalWidth/Height` 800×533, `complete:true`, снимката
изпълва цялата 16:9 рамка без прекъсване.

**Урок:** при бъдещ репорт "снимката изглежда счупена/наполовина" —
провери ПЪРВО дали елементът реално е `object-fit:cover` (не може
структурно да остави празно място) срещу `contain`/`fixed`-height
container (може) — това веднага стеснява дали причината е композиция
на изображението или неуспешно зареждане.

## Основни функции

Долна навигация (`.bnav`), 5 таба: **Начало / Процедури / Напомняне /
Очаквайте / Дневник**. Плюс страници извън навигацията: `page-profile`

`page-for-clinics`.

### Важни решения в тези функции

- **`sentNotifIds` вместо `notifs[].sent`.** Реален инцидент (25.07.2026):
  `notifs` масивът е client-owned и се презаписва ЦЯЛ при всяко календарно
  действие, затова `sent` флагът в него периодично се "възкресяваше" на false
  от остаряло локално копие и cron-ът препращаше вече доставени известия.
  Сега sent статусът живее в отделно map поле `sentNotifIds` (dot-notation
  update, атомарно per-key), което rules-ите заключват като изцяло сървърно.
  Проблемът стана **структурно невъзможен**, не просто закърпен.
- **`claimNotif()` — Firestore транзакция.** Cloud Scheduler има
  at-least-once доставка (може да гръмне два пъти). Транзакцията "заявява"
  правото да прати конкретно известие; който не успее — пропуска.
- **`nextReminderAt`** — ISO string на най-близкото непратено напомняне, за
  да може cron-ът да прави евтина range заявка (`where nextReminderAt <= now`)
  вместо да сканира цялата `users` колекция. Пресмята се на две места, които
  **трябва да остават синхронизирани**: `computeNextReminderAtServer()`
  (сървър) и `window._computeNextReminderAt()` (клиент). Лексикографското
  сравнение на ISO низове съвпада с хронологичното — затова работи.
  Има и self-healing клон: ако в даден цикъл не е claim-нато нищо,
  `nextReminderAt` се преизчислява ръчно, иначе потребителят би влизал в
  заявката завинаги.
- **48-часов прозорец** — напомняния, закъснели с повече от 48ч, никога не
  се пращат (иначе при връщане от отпуска се изсипват наведнъж).
- **`sofiaWallTimeToUTC()`** — потребителят въвежда стенен час за София;
  превръщането в UTC минава през `Intl.DateTimeFormat`, не през фиксиран
  offset (лятно/зимно часово време).
- **Идемпотентност на Firestore тригерите** — `meta/*/processedEvents/{event.id}`
  документ с TTL 30 дни. Eventarc също е at-least-once.
- **Referral anti-fraud** — кодът се преизчислява НЕЗАВИСИМО от подадения
  `referrerUid` (`generateReferralCode()`, SHA-256 от uid) и се сравнява,
  защото rules позволяват на клиента да създаде pending документ с
  произволен `referrerUid` — атакуващият контролира и двете полета в един
  и същ write, така че самосъгласуваност не доказва нищо. Отделно наградата
  изисква **потвърден имейл** на доведения и **първи diary entry** (не самата
  регистрация).
  `generateReferralCode()` е byte-идентичен близнак на `_generateReferralCode()`
  в `index.html` — **промяна на алгоритъма изисква синхронна промяна и на
  двете места**.
- **Anti-enumeration в `sendBrandedPasswordReset`** — винаги връща `{ok:true}`,
  и за несъществуващ имейл, и за throttled заявка. Throttle-ът се проверява
  ПРЕДИ `generatePasswordResetLink`, за да важи и за непознати имейли
  (иначе enumeration probing е нелимитиран). Две граници в една транзакция:
  3/час на имейл + 20/минута глобално. Глобалната е важна, защото функцията
  споделя SMTP акаунта с `notifyOnClinicInquiry` — spam-натоварване би
  маркирало акаунта при Zoho и би счупило и B2B известията.
- **Брандираният reset линк** — Firebase генерира линк към
  `after-care-treatment.firebaseapp.com`, защото glowtrack.eu е GitHub Pages,
  не Firebase Hosting. Затова функцията изважда `oobCode`-а от генерирания
  линк и строи собствен URL `https://glowtrack.eu/?mode=resetPassword&oobCode=...`
  — `index.html` сам го разпознава и показва форма за нова парола.
  glowtrack.eu ТРЯБВА да остане в Authentication → Settings → Authorized
  domains, иначе `generatePasswordResetLink` гърми.
- **`deleteAccountData` е сървърна нарочно** — `admin.auth().deleteUser()`
  няма "recent login" изискване, за разлика от клиентския `deleteUser()`.
  Старата клиентска логика можеше да изтрие данните и да остави Auth акаунта
  като "празна черупка" при изтекла сесия.

## Marketplace за клиники — В ПРОЦЕС (само бекенд основата засега)

Дългосрочен план: двустранен marketplace (клиенти ⇄ клиники) за сравнение
на цени по процедура, с GlowTrack като посредник (роли, регистрация с
ЕИК/БУЛСТАТ, плащане, аналитика). Пълният план — роли, стъпаловидна пътна
карта, конкурентна среда, отворени решения — засега живее в отделен работен
документ извън repo-то (обсъждан с потребителя, не е committed тук).

**Направено в кода до момента — само нотификационната основа, нищо друго:**
- `firestore.rules` — нови колекции `clinics/{clinicId}` (публично четими,
  писани само от админ — клиника още няма собствен self-serve панел за
  редакция на профила си) и `clinic_prices/{priceId}` (клиниката пише само
  собствените си редове, `clinicOwnerUid == request.auth.uid`, само след
  `clinics/{uid}.status == 'approved'`; писането НИКОГА не е заключено зад
  плащане — решено изрично, "въвеждането не спира" дори след пробния период,
  плащането ще гейтва бъдеща видимост за клиенти, не самото писане).
  `admin_notifications/{notifId}` — пълни се САМО от Cloud Function (Admin
  SDK), клиентът никога не създава запис сам; `update` е ограничено до точно
  `reviewed`/`reviewedAt`, за да не презаписва "Прегледай" бутона случайно
  останалите полета.
- `functions/index.js:notifyOnClinicPriceChange` — `onDocumentWritten` (не
  `onDocumentCreated` като `notifyOnClinicInquiry` — трябва да хване И ново
  качване, И редакция) на `clinic_prices/{docId}`. Строи кратко резюме
  какво се е променило (сравнява `before.price`/`after.price`), пише го в
  `admin_notifications` И праща имейл през същия Zoho SMTP механизъм като
  `notifyOnClinicInquiry`. Изтриване на ред (delete на документа) НЕ известява
  — собственик, чистещ собствен ред, не е нередност за преглед.
- `index.html` — нова секция "Известия от клиники" в админ панела
  (`loadAdminClinicNotifications()`/`markClinicNotifReviewed()`), веднага
  до "Съобщения от потребители" (`loadAdminInbox()`), СЪЩИЯТ визуален модел
  (`.admin-inbox-item` класовете, преизползвани directly). Всеки запис
  показва клиника + резюме + дата; "Прегледай" САМО маркира `reviewed:true`
  — записът остава в историята завинаги, за да може по-късно да се
  проследи какво вече е било проверено за релевантност на цената (изрична
  заявка на потребителя — "да мога да проследявам... дали реално цените
  им релевантни").

**Втора стъпка — реалната форма за регистрация на клиника** (вече не само
мокъп): нова секция в `#page-for-clinics` ("Сравнение на цени по процедура"),
ОТДЕЛНА от съществуващата обща B2B форма отгоре (тя пише в `clinic_inquiries`
— общ маркетингов lead за реклами/партньорства; новата е конкретна
идентификационна регистрация с ЕИК/БУЛСТАТ за marketplace-а за сравнение на
цени, пише в нова колекция `clinic_registrations`). Умишлено само на
български (без `CT[lang]` threading като горната секция) — БУЛСТАТ е
специфично за българска регистрация.
- Полета: име, ЕИК/БУЛСТАТ, ДДС регистрация (Да/Не превключвател,
  `.vat-toggle-btn`/`setRegVat()`), адрес, уебсайт (по желание), телефон,
  имейл, лице за контакт. БЕЗ качен документ — премахнато по изрична заявка
  преди да стигне до код (верификацията минава през самите данни, не файл).
- `firestore.rules` — `clinic_registrations/{docId}`: `allow create: if true`
  (клиниката още няма акаунт в момента на подаване), `read/update/delete`
  само `isAdmin()` — огледален модел на `clinic_inquiries`.
- `functions/index.js:notifyOnClinicRegistration` (`onDocumentCreated`) —
  известява по имейл И пише в **СЪЩАТА** `admin_notifications` колекция
  като `notifyOnClinicPriceChange` (`type:'clinic_registration'`) — умишлено
  ЕДНА обща лента "активност от клиники" в админ панела
  (`loadAdminClinicNotifications()`), не два отделни списъка за преглед.
- `clinicId` в `admin_notifications` е `null` за регистрации (клиниката
  все още няма Firebase Auth uid на този етап) — различно от известията за
  промяна на цена, където `clinicId` сочи реалния собственик.
- Проверено с Playwright (Firebase SDK-ът не се зарежда в тази среда,
  мрежата към `gstatic.com` е блокирана — известно ограничение, документирано
  и другаде в тоя файл): отваряне на формата, ДДС превключвателя, валидация
  на празни задължителни полета, и преходът към екрана "Чака одобрение" (със
  stub-нат `F().addDoc`) — всичките минават чисто, нула JS грешки. Самият
  Firestore `addDoc()` извик следва ТОЧНО същия установен модел като
  `clinic_inquiries`/`feedback` другаде във файла, не е тестван "на живо"
  срещу реален Firebase в тази среда.

**Трета стъпка — реалното одобрение вече създава Firebase Auth акаунт.**
`functions/index.js:approveClinicRegistration` (`onCall`, само за
`ADMIN_UID`) — сървърна нарочно, защото `admin.auth().createUser()`
съществува само в Admin SDK; клиентският Firebase SDK изобщо няма метод за
създаване на акаунт за трета страна, значи firestore.rules физически не
биха могли да заместят тази функция, колкото и стриктни да са.
1. Чете `clinic_registrations/{id}`; ако вече е `status:'approved'` —
   отказва (идемпотентност, пази от двоен `createUser()` при двоен клик).
2. `admin.auth().createUser({email,...})` — при `auth/email-already-exists`
   НЕ преизползва тихо съществуващия uid (имейл, споделен с личен
   потребителски акаунт, изисква ръчна преценка, не автоматично сливане на
   самоличности) — връща изрична грешка на админ панела вместо това.
3. Създава `clinics/{uid}` документ (копира профилните полета от
   регистрацията + `status:'approved'`), маркира `clinic_registrations/{id}`
   като `approved` с `approvedUid`.
4. Праща имейл с линк за задаване на парола — СЪЩИЯТ `oobCode` механизъм
   като `sendBrandedPasswordReset` (glowtrack.eu е GitHub Pages, не Firebase
   Hosting, затова линкът се строи ръчно от извлечения `oobCode`, не се
   ползва директно генерирания Firebase линк). Best-effort — неуспех тук НЕ
   отменя вече създадения акаунт, само липсва имейл; клиниката пак може да
   мине през обичайния "Забравена парола" екран.

`index.html` — ново табло "Клиники — чакащи одобрение" в админ панела
(`loadAdminClinicPending()`), СЪСЕДНО на "Известия от клиники", не същото —
там е обикновен feed, тук са конкретни редове с бутони "Одобри"/"Откажи".
"Одобри" вика `approveClinicRegistration` през `httpsCallable`
(`window._callApproveClinicRegistration`, регистриран до
`_callSendPasswordReset`); "Откажи" е обикновен клиентски `updateDoc`
(`status:'rejected'`) — не изисква Cloud Function, защото не създава акаунт.
Заявката `where('status','==','pending')` е БЕЗ `orderBy` (сортирането е
клиентско, `Array#sort` по `createdAt`, същия похват като `loadAdminInbox()`)
— `where`+`orderBy` на различни полета би изисквало съставен Firestore
индекс, който не съществува и не се създава автоматично.
Проверено с Playwright (stub-нат `F()`/`_callApproveClinicRegistration`,
реален Firebase не се зарежда в тази среда): списъкът се сортира правилно
по дата (най-новата отгоре), "Откажи" вика `updateDoc` с точните полета,
"Одобри" вика Cloud Function-а с правилния `registrationId` и заключва
бутона докато чака — нула JS грешки.

**ИЗРИЧНО ОЩЕ НЕ Е ПОСТРОЕНО** (следващи, отделни стъпки от пътната карта):
клиничен self-serve панел за редакция на цени (клиниката може да влезе с
новия си акаунт, но още няма какво да прави там), `role:'clinic'` изрично
поле (в момента самото съществуване на `clinics/{uid}` документ Е сигналът
"това е клиничен акаунт" — няма отделен флаг), Stripe продукт/плащане за
клиника, каквато и да е логика "невидимо докато не плати".

**Изисква ръчно действие от потребителя, извън repo-то, преди да проработи
на живо:** `firestore.rules` НЕ се деплойва от CI (виж раздела "Работен
процес при промени" по-долу) — новите правила (`clinics`/`clinic_prices`/
`admin_notifications`/`clinic_registrations`) изискват `firebase deploy
--only firestore:rules` ръчно, ВСИЧКИ наведнъж (правилата все още не са
пуснати от предната стъпка). `functions/index.js` промените
(`notifyOnClinicPriceChange`, `notifyOnClinicRegistration`,
`approveClinicRegistration`) СЕ деплойват автоматично от
`deploy-functions.yml` при push към `main`.

## Push известия и service worker — прочети това преди да пипаш `sw.js`

Дълга поредица от реални бъгове с **двойни известия**. Всяка от тези
поправки е останала в кода с коментар — не ги връщай назад:

1. **Само ЕДИН service worker на scope.** Не регистрирай отделен
   `firebase-messaging-sw.js` — `sw.js` съдържа и Firebase Messaging.
   Два SW на един scope се борят и печели последният, който се
   пререгистрира при всяко зареждане; push известията спират тихо (v5).
2. **DATA-ONLY payload от сървъра** (v7). Ако payload-ът има `notification`
   поле, Firebase Web SDK показва системно известие САМ, паралелно с нашия
   `onBackgroundMessage` handler → 1 съобщение = 2 известия. Затова
   `sendScheduledReminders` и `notifyOnUserMilestone` пращат САМО `data`,
   а `sw.js` чете `payload.data.title`/`.body`.
3. **`clients.claim()` е премахнат** от `activate` handler-а (v8). С него
   старият и новият SW можеха да обработят едно и също push събитие
   паралелно. Без него новият SW поема контрол при следващото зареждане,
   а Firebase auth сесията се пази коректно.
4. **Постоянна дедупликация през Cache Storage** (`glowtrack-seen-notifs`) —
   оцелява рестарт на service worker-а, за разлика от обикновена променлива.
5. **Badge иконата** сочеше към несъществуващ `favicon-32.png` (404 при всяко
   известие) — сменена на `icon-192.png` (v9).

Има и суров `push` listener, който брои физическите събития преди Firebase
SDK-ът да ги обработи — ако там броячът се вдигне 2 пъти за едно известие,
дублирането идва от ОС/APNs, не от нашия код.

**Fetch стратегия:** HTML и всичко от firebase/google/gstatic домейни —
винаги от мрежата, никога от кеша. Само статичните assets са cache-first.

**Разрешението за push** се иска при явно действие, не при отваряне.
`initPushNotifications(silent)` се вика автоматично от `onAuthStateChanged`
без toast-ове; изричният тап на "Включи" показва toast-ове. Токенът се пише
във Firestore само ако наистина се е сменил (иначе всеки pageload = излишен
write + race при бързо reload).

### Известно несъответствие: `?v=` при регистрацията

`sw.js` е на **v9** (`CACHE = 'glowtrack-v9'`), но `index.html` го регистрира
като `./sw.js?v=8`, а вътрешният `console.log` в `sw.js` още пише "v8 активен".
Query параметърът съществува точно за да принуди iOS Safari (известен с
упорито кеширане на SW файлове) да третира файла като нов ресурс. **При
следващо вдигане на версията вдигни и трите**: `CACHE`, `?v=` в регистрацията
и текста на `console.log`.

## Сигурност

- **`esc()` навсякъде за потребителски текст**, вкарван в `innerHTML` темплейт
  литерали — feedback текст, персонални стъпки, дневникови бележки,
  заглавия на календарни събития, ехо в AI чата. Систематична поправка от
  одита (25.07). При нов код с темплейт литерал и потребителска стойност —
  `esc()` е задължителен.
- **Заключени server-only полета** — `referralCount`, `unlockedRewards`,
  `sentNotifIds`. `create` и `update` са РАЗДЕЛЕНИ в rules умишлено:
  `diff(resource.data)` изисква съществуващ `resource`, а при create той е
  `null` и правилото гърми, което rules engine-ът оценява като deny.
  **Това счупи регистрацията ИЗЦЯЛО в production** (потвърдено с E2E тест
  28.07): setDoc-ът за новия профил гърмеше с permission-denied → тригерваше
  rollback-а, който триеше току-що създадения Auth акаунт → потребителят
  виждаше "грешна парола" със същите данни, без никаква следа защо.
  **Не обединявай двете правила обратно.**
- **Orphaned Auth акаунти** — при регистрация, ако профилният документ не се
  създаде, Auth акаунтът се трие (rollback), за да остане имейлът свободен
  за чист повторен опит. Плюс self-healing backfill в `onAuthStateChanged`
  за акаунти, стигнали дотам преди този фикс.
- **Storage** — `diary-photos/{uid}/` само за собственика, макс 5 MB, само
  `image/*`; `app-assets/` публично четими, качват се ръчно от админ.
- **Снимките се компресират в браузъра преди качване** — макс 800px по
  дългата страна, JPEG качество 0.75, макс 3 снимки на слот
  (общи / преди / след).
- API ключът на Anthropic никога не е в клиентския код — минава през
  `askAiAssistant`.

## Постоянни правила

- **Само SVG икони, никога emoji** за елементи на интерфейса. Има цяла
  система: `ICO_DEFS` (56 ключа) + helper `ic(key, size)`, който връща
  `<svg class="gt-ico">` с `stroke="currentColor"`, за да наследява цвета.
  Всяко семантично значение е сведено до един от ~56 ключа, преизползвани
  навсякъде. При нова иконка — нов запис в `ICO_DEFS`, не суров emoji.
  *(Остатъци, оцелели от преди системата: 🎂 на ред ~1452, ✅/⚠️ на ~7547–7548,
  🎉 на ~8526, ✓ в toast на ~2355. Ако пипаш тези редове по друг повод —
  замени ги с `ic(...)`.)*
- **`--gold` е един-единствен източник на акцента.** Роз-златната тема
  предефинира `--gold`/`--goldlt` на ниво `body.theme-rosegold` — точно
  затова не се пипат стотиците съществуващи `var(--gold)` употреби.
  Не въвеждай втори акцентен механизъм.
- **Топбарът е `position:fixed`**, а не `sticky` (промяна от 10.08 — при
  sticky се движеше при скрол). Реалната му височина зависи от
  `safe-area-inset-top` (различен notch на всяко устройство), затова се
  ИЗМЕРВА при зареждане и се пази в `--topbar-h`; `.app` и `#offline-banner`
  компенсират с нея. Не заковавай височината на топбара с константа.
- **Офлайн лентата е ПОСТОЯННА, не toast.** Остава видима докато няма
  мрежа — за да е ясно, че показаните дневник/реклами са последно
  кешираните данни, а не актуални.
- **Изтриване на записи ≠ почистване.** `notifs` по-стари от 30 дни се
  чистят автоматично; **`calEvents` НИКОГА** — те са видима история за
  потребителя, триенето им е загуба на данни.
- **Не презаписвай масив от стар локален snapshot.** И `notifs`, и
  `calEvents` минават през merge-safe sync (`syncNotifsFS`,
  `syncCalEventsFS`), който чете текущото Firestore състояние и прилага само
  конкретното действие (add/update/delete). Blanket overwrite губи промени,
  направени от друго устройство между зареждането и записа.
- **Всеки провален запис в облака показва toast.** Централизирано в
  `syncNotifsFS`, не дублирано в ~13-те call site-а. Без това потребителят
  не научава, че локално запазеното напомняне никога не е стигнало до
  сървъра.
- **Езикът е bg/en в `T` обекта, но B2B landing-ът е bg/en/de/ru в `CT`.**
  Добавянето на език в `CT` иска само нов `CT.xx` блок + бутон в маркъпа —
  логиката се извежда от `Object.keys(CT)`, не от закован списък.
- **Тъмната тема е по подразбиране** (`gt_dark !== '0'`), не светлата.

## Известни ограничения и находки

Неща, които са ВЕРНИ за кода в момента. Нито едно не е блокер, но всяко е
капан, ако не се знае.

1. **Няма `<!DOCTYPE html>`.** Файлът започва направо с `<html lang="bg">`,
   тоест страницата се рендира в **quirks mode**. Приложението очевидно
   работи така и целият CSS е нагласен спрямо това. Добавянето на doctype
   би превключило на standards mode и **може да размести layout-а** — не е
   промяна "за чистота", изисква реален тест на устройство.
2. **Дублирани ключове в `T`** — 16 в `bg` и 14 в `en`. JS взима ПОСЛЕДНАТА
   дефиниция, а част от дубликатите имат **различни стойности**, тоест
   първата версия е мъртва: `noReminders` ('Все още няма напомняния' →
   'Няма напомняния'), `notifPast` ('Минало' → 'Минали'), `addStep`,
   `notifPastSection`, `searchClinics`, `searchProducts`. Ако редактираш
   някой от тези низове и промяната "не се вижда" — редактираш мъртвия
   дубликат.
3. **`window._cache.CACHE_TTL` е 2 минути, а коментарът до него казва
   "5 minutes".** Стойността е правилната, коментарът е стар.
4. **`functions-index.js` в корена на repo-то е МЪРТЪВ файл** — стара копия
   (288 реда) на `functions/index.js` (820 реда). Не се деплойва, не се
   копира в `dist/`, не се чете от нищо. Ако търсиш код на Cloud Function —
   истинският е в `functions/`. Кандидат за изтриване.
5. **Твърдо закодиран български текст извън `T`** — напр. "⚠️ Датата е в
   миналото" (~7548) и целият блок за streak на рутината (~9345+,
   "Пълна рутина!", "завършени", "Изпълнена на") се показват на български
   и при английски интерфейс.
6. **Известен и приет race при регистрация** — `createUserWithEmailAndPassword`
   тригерира `onAuthStateChanged` асинхронно, докато регистрационният поток
   продължава към своя `setDoc`. При неудачен ред документът се записва два
   пъти с еднакви полета (само `createdAt` варира). Документирано в кода
   като нарочно непоправено — не поврежда данни.
7. **`referral` не се преоценява по-късно.** Ако доведеният направи първия
   си запис в дневника ПРЕДИ да потвърди имейла си, referral-ът остава
   `pending` завинаги (не `rejected`, но и никога не се кредитира). Приет
   компромис срещу mass fake акаунти.
8. **Няма тестове, няма линтер.** Единственият автоматичен пазач е
   `npm run build` — terser гърми при синтактична грешка, а
   `verifyHandlerNamesSurvive` гърми, ако инлайн handler изчезне.
9. **Целият личен state на един потребител е в ЕДИН документ `users/{uid}`**
   (`notifs`, `calEvents`, `favs`, `cycleData`...). Firestore таванът е 1 MiB.
   Дневниковите записи са отделни документи, така че реален риск има само при
   екстремно много напомняния/календарни събития — но лимитът съществува и
   не се следи никъде. (В iForget има `checkDocSize()` за същия проблем.)
10. **`find_emoji.py` / `find_toasts.py`** в корена са еднократни dev
    помощници (търсене на emoji и на toast низове). Не участват в build-а.

## Работен процес при промени

1. `git pull -q origin main` преди всяка промяна.
2. Редакция на `index.html` (и/или `functions/index.js`, `sw.js`, правилата).
3. **`npm run build`** — задължително преди push. Това е и синтактичната
   проверка (terser), и проверката, че инлайн handler-ите са оцелели.
   Ако някога добавиш нов инлайн `onclick`, увери се, че броят в реда
   `verified N inline-handler function name(s)` расте.
4. `git add -A && git commit -m "..." && git push -u origin main`.
5. Изчакай ~30–60 сек и провери GitHub Actions run-а
   (`Deploy static content to Pages`) за `conclusion:"success"` преди да
   докладваш успех. Ако си пипал `functions/**`, провери и
   `Deploy Firebase Functions`.
6. Отговорът винаги е **на български**, с препратка към живия адрес
   `https://glowtrack.eu` и напомняне за hard refresh (браузърният/PWA
   кешът понякога пази старата версия — `Cmd+Shift+R`).

Промените в `firestore.rules` / `storage.rules` **НЕ** се деплойват от CI —
`deploy-functions.yml` пуска само `--only functions`. Правилата се качват
ръчно от собственика с `firebase deploy --only firestore:rules,storage`
или през Firebase Console. Ако промениш правило, кажи го изрично.

Ако промяна изисква действие извън repo-то (Firebase Console, Stripe, DNS,
secrets) — кажи го ЯСНО и отделно, не го споменавай мимоходом.
